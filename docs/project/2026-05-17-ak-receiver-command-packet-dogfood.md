## Receiver command packet usage

The preflight result included `receiver_command_packet.commands` with phase-labeled templates for:

- ACK;
- claim;
- contract inspection;
- done-contract authoring;
- guardrail authoring;
- validation;
- validation evidence;
- dogfood/finding evidence;
- task completion;
- final intercom receipt.

Used directly:

- `claim_target_task` was used as `ak task claim 3090 --agent pi`.
- `inspect_existing_contract` was used as `ak task contract show 3090 -F json`.
- `set_done_contract` was used with the packet's completion kind, outcomes, validation commands, and evidence classes.
- `set_handoff_guardrails` was used with the packet's intercom/AK authority invariants and rollback boundary.
- The validation command list was used as the required validation set.
- The final receipt field list was used as the final response shape.

Adapted:

- The ACK was sent as an intercom reply rather than by executing the comment-template text.
- The guardrails were extended with this repo's explicit file boundary: only `docs/project/2026-05-17-ak-receiver-command-packet-dogfood.md` may be mutated, and `docs/_core/**` remains forbidden.
- Evidence and completion commands used concrete JSON details and actual evidence/commit identifiers after validation rather than the packet placeholders.

## Dogfood finding

The receiver command packet substantially reduced manual translation after preflight acceptance.

What worked:

- The command packet made the expected receiver phases explicit and ordered.
- It separated coordination-only intercom steps from AK-owning-repo mutation steps.
- It carried the exact completion kind, outcomes, validation commands, evidence classes, and final receipt fields into the receiver session.
- The receiver could adapt templates without inventing the task lifecycle from prose.
- Authority stayed clear: the packet did not execute commands, claim/complete tasks, record evidence, send intercom messages, or mutate FCOS/source-owner surfaces.

Remaining gaps:

- Commands are still shell templates with placeholders, so the receiver must safely substitute agent names, JSON evidence, result payloads, and final commit ids.
- The packet does not yet include a machine-readable diff of direct-vs-adapted commands for evidence capture.
- The `expected_peer` value is still informational rather than a hard active-session identity gate.
- Envelope delivery remains a shared filesystem path coordinated over intercom.

## SF12/IW24 implication

This is positive evidence for the SF12/IW24 direction: once read-only preflight accepts a handoff, a generated receiver command packet can carry enough lifecycle structure to reduce manual prose parsing while preserving owner boundaries.

The next product improvement is to make command-packet consumption more typed: receivers should be able to report which command templates were used, adapted, or skipped as structured evidence without manually writing that mapping.

## Non-actions and preserved boundaries

This dogfood did not:

- mutate `docs/_core/**`;
- change source code or supported capability states;
- mutate FCOS control-board, Prompt Vault, Pi/runtime, KES, ROCS, templates, steward/publication, Oracle/DSPx, or unrelated files;
- treat intercom as task/evidence/completion authority;
- cause the command packet to execute commands automatically;
- claim SF12 or IW24 complete by itself.
